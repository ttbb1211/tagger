# 曲库切换不再被待审核任务阻挡

## 背景

设置 → 音乐目录里添加或切换曲库时，后端 `rejectLibraryMutation` 用的是 `jobs.Manager.HasActive`。这个谓词把 `waiting`、`running`、`review` 三种状态一律视为「活跃」，于是一个停在 `review` 的抓取任务会永久锁住曲库切换。

实际情况里 `review` 只是持久化的 UI 状态，不是正在执行的文件改动：

- 它不占用 worker —— `store.ClaimJob` 只领 `state = waiting` 的任务，队列不会因为它堵住。
- 它不持有任何文件句柄，也不会有写入落在旧根目录上。
- 一次残留的测试抓取（或用户中途离开审核页）就会让「换音乐目录」彻底不可用，只能先把审核走完或丢弃，而走完审核又要再抓一次。

`internal/jobs` 里本来就有正确的谓词：`HasBlockingFileWork` 只认 `waiting` / `running` 状态下的 `scan`、`write`、`batch_edit`、`organize` 四类任务，注释明确写了 review 不算文件改动。它此前只用于两处（目录对账、fsnotify 实时索引），没有接到曲库切换上。

## 行为

`rejectLibraryMutation` 改用 `HasBlockingFileWork`：

- 仍然拦截：等待中/运行中的扫描、写入、批量编辑、整理文件任务 —— 这些任务的目标根目录会在换根后失效，必须挡。
- 不再拦截：待审核（`review`）任务，以及只在网络上抓取元数据的 `match` 任务。
- 冲突时的提示语随之改为「存在运行中的扫描或写入任务，请完成或取消后再修改曲库」，不再提「待审核」。

`HasActive` 保留但补了文档注释，说明它会连 review 一起算作活跃、不能用于「文件是否正在被改动」这类判断，避免后续调用点再踩同一个坑。

## 已知副作用

换根后旧曲库的审核任务会「失联」：任务仍留在任务中心，但打开审核页时 `listMatchItems` 返回的 trackId 在新曲库里解析不到，页面会落到「没有可显示的审核结果」分支。

这是刻意接受的取舍 —— 任务没有损坏任何数据，用户可以在任务中心直接丢弃它；比「被一个走不完的审核永久锁住曲库切换」要好。若日后希望更彻底，可以在任务中心按当前曲库过滤任务列表。

## 验证

- `internal/server` 新增 `TestLibrarySwitchIgnoresPendingReviewJobs`：队列里放一个 `kind=match`、`state=review` 的任务，切换曲库应返回 202 并排队 `scan`。
- 既有 `TestLibrarySwitchQueuesSafeBackgroundJob` 覆盖「`scan` + `waiting` 仍然返回 409 `library_switch_busy`」，未受影响。
- `GOCACHE=/tmp/tagger-go-cache go test ./...` 全绿。
