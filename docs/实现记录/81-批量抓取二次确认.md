# 批量抓取二次确认

## 背景

曲库页的「批量补全」（选择栏里叫「抓取元数据」）此前是点一下就直接排队：

```
LibraryPage.openReviewSelection()  →  onOpenReview(ids)
  →  App.openReview → 切到 review 路由
  →  ReviewPage 的加载 effect 里 createMatchJob(ids)  ← 任务在这里就建好了
```

中间没有任何确认，也不看队列里是否已经有同类任务。实测踩到的场景：用户想结束一个卡在「等待审核」的旧任务，重新点了一次批量补全，结果旧任务还在、又平白多排了一个需要审核的抓取。

## 实现

把「建任务」这一步从「点击即执行」改成「先确认、再执行」：

- `openReviewSelection` 仍然先做原有的两个前置校验（单次上限、是否含未索引曲目），解析出这一批的 trackId 后**不再直接跳转**，而是打开一个 `ConfirmDialog`。
- 确认框内容由 `reviewConfirmDescription(count, pending)` 生成：
  - 本次将抓取几首；
  - 队列里是否已有 `match` 任务在执行或排队（含最早开始时间）；
  - 是否已有批量抓取停在等待审核（含最早时间与累计曲目数），并提示旧任务可在任务中心「丢弃审核任务」处理；
  - 两者都没有时明确写「当前没有进行中或待审核的批量抓取」，回答「是不是已经抓过了」。
- 待确认的任务列表来自 `listJobs()`，前端按 `kind === 'match'` 且状态为 `review / running / waiting` 过滤，**不新增后端接口**。查询失败时降级为「无提示」，不会因为读不到队列而拦住用户。
- 确认按钮文案是「开始抓取」，走 `confirmTone="primary"`（`ConfirmDialog` 新增的可选属性，默认仍是红色 `danger`，不影响既有调用点）。

## 附带修正

任务中心「丢弃审核任务」的确认文案原为「这只会删除本次抓取的候选和审核快照」，但后端 `Manager.Cancel` 只把任务状态置为 `cancelled`，并没有删除 `match_items`（仓库里没有对应的删除实现）。文案改为与实现一致：「丢弃只会把该任务标记为已取消，不会修改任何音乐文件，也不会删除已抓取的候选。丢弃后曲库切换不再受它阻挡。」

## 验证

- `LibraryPage.test.tsx` 新增两条用例：
  - 点「批量补全」后先出现确认框、`onOpenReview` 未被调用，点「开始抓取」后才带上 trackId 调用；
  - 队列里存在 `review` 与 `running` 的 match 任务时，确认框里出现对应的数量与曲目数提示，点「取消」不会建任务。
- `npm test` 全绿；`npx tsc --noEmit` 通过。
